# Φ PhiCloud

**Sovereign web services for the PhiOS ecosystem.**

PhiCloud is the proposed **local-first service backbone** for PhiOS Desktop, WebOS, Mobile, and ecosystem applications such as PhiMail and PhiServe. The project is designed to provide service discovery, identity integration, storage, synchronization, observability, and optional hosted infrastructure without making the cloud mandatory.

> **Status: foundation / design stage.** This repository is being initialized. No hosted service, production identity provider, mailbox delivery, account sync, or deployed infrastructure is claimed.

## Operating principles

- **Sovereignty:** PhiOS must remain usable offline and without a PhiCloud account.
- **Interoperability:** use open protocols, documented exports, and portable data.
- **Capability is not authority:** signing in does not grant permission to execute actions on a user's device.
- **Plain Sovereign first:** independently functional infrastructure, even if advisory orchestration is offline.
- **Advisory before automation:** observable recommendations and audit records before privileged control.
- **No fake availability:** registry declarations are not runtime health checks.
- **No secrets in static sites, public manifests, source control, or browser bundles.**

## Naming and responsibilities

| Component | Responsibility |
| --- | --- |
| **PhiID** | Account identity, OIDC sign-in, passkeys, user lifecycle (future service) |
| **PhiMail** | Email client, mailbox experience, and eventual optional hosted mail |
| **PhiShield** | Policy enforcement and access control at service boundaries |
| **PhiVault** | Object storage, files, backups and user-directed exports |
| **PhiSync** | Opt-in cross-device data synchronization |
| **PhiCompute / PhiBase** | Compute and database substrate |
| **PhiNet / PhiRoute** | Private network and service discovery |
| **PhiTrigger** | Governed functions, workflows and events |
| **PhiEye** | Health, telemetry, operator explanations, audit |
| **PhiServe** | Independently governed local AI serving; remote access is not implied |
| **PhiKernel bridge** | Advisory-only, normalized contract, no internal implementation in this public repo |

**PhiMail is the user-facing account doorway, not the security root.** Accounts use stable opaque identifiers (OIDC `sub`), while mailbox addresses are mutable login/contact aliases. Mail delivery and email recovery must never become the only access path to the operating system.

For PhiMail R1's **development-only service declaration adapter**, see [the PhiMail registry compatibility guide](docs/PHIMAIL_ADAPTER_R1.md). A successful inventory read never confirms service health or identity.

See the [architecture](docs/ARCHITECTURE.md), [PhiID ↔ PhiMail identity contract](docs/PHIID_PHIMAIL_IDENTITY.md), and [roadmap](docs/ROADMAP.md).

PhiID and PhiMail now share a **local development OIDC issuer** through independent clients. PhiCloud still exposes **no identity gateway or mail API**; see [R2 verified-identity boundary](docs/PHIMAIL_IDENTITY_R2.md).

## R4: Two-user resource ownership isolation (disposable localhost demo)

The optional, separately gated R4 resource demo adds short-lived **memory-only** records owned by the exact Keycloak-verified `(issuer, subject)` pair. A client with `phicloud.demo.read` can list/read only its own records, while `phicloud.demo.write` allows only explicitly acknowledged create/delete. Two otherwise valid accounts cannot access each other's record IDs. Each request repeats fresh Keycloak token introspection, so upstream revocation immediately denies access.

**Both** `PHICLOUD_ENABLE_OAUTH_DEV=1` **and** `PHICLOUD_ENABLE_OWNER_DEMO=1` are required, plus the private confidential-client secret. Disabled by default. The records are generated by the server, contain no user content, expire after ten minutes and vanish on restart. No actual cloud storage, device permission or mailbox exists.

See [R4 ownership isolation and two-real-user Keycloak tests](docs/R4_OWNER_ISOLATION.md).

## R3: Protected localhost demo resource via real Keycloak tokens

The optional **PhiCloud R3 resource-server gate** validates a real OAuth 2.0 access token through Keycloak confidential-client introspection on fixed IPv4 loopback. It checks `active`, exact issuer, `aud=phicloud-resource-dev`, `scope=phicloud.profile.read`, expiry and subject on **every** request. A disabled or revoked token fails closed, and arbitrary PhiID display exports or consent receipts never grant access.

The new `/v1/private/profile` route returns only a pseudonymous, *synthetic local test profile* with explicit `cloud_storage_access:false`, `mailbox_access:false`, and `phios_effect_authority:false`. The existing public `/v1/services` registry remains unchanged.

**Disabled by default**. Requires `PHICLOUD_ENABLE_OAUTH_DEV=1` and a private `PHICLOUD_OAUTH_CLIENT_SECRET` for a dedicated confidential Keycloak development client. No hosted login, file storage, authorization for real resources or production deployment is implemented.

See [R3 scope, setup, real-provider CI and limitations](docs/R3_LOCAL_OAUTH_GATE.md).

## R4: verified PhiID identity → PhiShield (development only)

The [R4 local identity-to-PhiShield bridge](docs/R4_PHIID_SHIELD_BRIDGE.md)
now derives a **fixed synthetic profile-read** action directly from a
freshly Keycloak-introspected PhiID access token. A separate consent
verifier and signed ANC advisory are required before the reference
policy can return a non-authoritative `CANDIDATE`.

The real-Keycloak CI workflow checks actual login, missing consent,
wrong scope/audience and upstream revocation. Consent and risk signing
in this test are disposable **synthetic fixtures**, not proof of live
human consent or a deployed ANC security service.

This adds **no** public policy API, general resource authority, mail/file
access, or device control. Login never grants PhiOS effects.

## R5: one-use local resource-owner review (prototype)

The [R5 in-process owner and consent state machine](docs/R5_LOCAL_OWNER_CONSENT.md)
now attaches the **synthetic self-profile** to the issuer/subject pair obtained
through fresh Keycloak access-token introspection. It stages an exact-action
review, supports a local terminal acknowledgment, consumes approval **once**,
and cancels pending approvals when the synthetic owner is revoked.

Its scope is deliberately fixed to `profile.read` on
`profile:synthetic-self`; no actual data storage, file/mail access or OS
effect is involved. The CI integration uses a genuine disposable Keycloak
session but **simulates** the terminal approval; it is not proof of a live
human's consent. A result is still only `DENY`, `REVIEW`, or non-authoritative
`CANDIDATE`.

The local ledger is not durable and has no remote API. It must not be
presented as production resource ownership or consent verification.

## R6: restart-safe local approval and revocation (POSIX prototype)

The [R6 SQLite-backed policy](docs/R6_DURABLE_LOCAL_CONSENT.md) adds an
**optional** private, operator-owned ledger for the existing synthetic
`profile.read` review flow. It preserves short-lived approved reviews,
spent request-ID tombstones, and owner revocations across process restarts.
A revoked owner cannot silently regain permission simply by signing in.

SQLite transactions serialize approval consumption across connections and
processes. The reference bridge still returns at most a non-authoritative
`CANDIDATE`, never permission to execute. The Keycloak integration CI
uses a **real disposable identity provider** with **simulated** operator
confirmation, plus restart/revocation denial tests.

This feature has **no HTTP endpoint**, real resource permission system,
human-presence attestation, encrypted database, public hosting or native
Windows ACL protection. It requires POSIX `0700` private-directory checks
(or a reviewed Linux/WSL development environment); Windows-native policy
creation fails closed until ACL auditing is designed. The existing
in-memory R5 reference remains the default.

## R7: Ed25519-signed operator review (optional local prototype)

The [R7 signed operator review](docs/R7_SIGNED_OPERATOR_REVIEW.md) uses
**real asymmetric Ed25519 signatures** over the exact staged synthetic
profile-read action. The private signing key stays **outside** PhiCloud;
the local SQLite ledger stores pinned public keys and permanent key-ID
revocation tombstones. Rotation enrolls a new key ID before revoking
the old one. Existing signed approvals are invalidated when their
signer key is revoked.

R7's signed-only evaluation path checks fresh PhiID identity, current
signer trust, one-use approval and authenticated ANC risk. Legacy
unsigned approvals cannot enter this path. Even success returns only
**non-executable `CANDIDATE`**, not OS authority.

The optional verifier requires
`python -m pip install -r requirements-operator.txt`. This
rung remains POSIX/local development only, with synthetic signatures
in CI and **no verified human signing ceremony**, hosted approval
service, real data permissions or native Windows ACL support.

## R9: WebAuthn user-verification gate for operator review (prototype)

The [R9 WebAuthn step-up](docs/R9_WEBAUTHN_OPERATOR_STEPUP.md) adds a
separate local **user-verified** path on top of R7's exact-action
Ed25519-signed review. A trusted local process may enroll a previously
verified WebAuthn public credential, issue one receipt-bound challenge,
and verify the authenticator's signature, RP/origin, user presence,
user-verification flag, and replay counter using pinned `webauthn`.

The private SQLite ledger preserves challenge/review state and credential
revocation. Revoking an operator credential or R7 signing key cancels its
outstanding reviews. Existing signed-only approvals are never relabeled
as user-verified. Success remains **non-authoritative `CANDIDATE`**.

**Not a live passkey experience:** There is no real registration
ceremony, hardware-backed user enrollment, browser UI, public API, or
device permission. CI uses genuine cryptographic WebAuthn syntax from
a synthetic authenticator and a real disposable Keycloak identity.
The origin is fixed to localhost for development only, and the
operator backend remains POSIX-only.

## R10: local browser passkey enrollment (experimental)

The [R10 local passkey enrollment tool](docs/R10_LOCAL_PASSKEY_ENROLLMENT.md)
adds a **real browser WebAuthn registration ceremony**, gated by a
one-use code from an explicitly started local terminal. It verifies
the returned authenticator credential through the pinned WebAuthn RP
library before storing its public key and sign counter in the private
R9 SQLite operator credential registry. The operator must already
have a trusted enrolled R7 signing key.

**Browser enrollment is not approval**: this does not authenticate the
operator's real-world identity, grant access, approve any signed review,
or let PhiCloud perform PhiOS effects. No public endpoint is added to
the default registry. The separate enrollment tool is localhost-only,
disabled by default, uses the existing fixed `http://localhost:8769`
origin, and requires a trusted Linux/WSL operator-controlled database.

CI verifies the full registration parser with **synthetic** WebAuthn
authenticator output. Actual browser/passkey hardware compatibility
requires manual validation. Real user identity binding and a
human-facing exact-action approval ceremony are future work.

## First executable milestone

The R0 prototype offers **local-only, read-only service declarations** and standard-library tests. It is not an IAM server, mail server, storage host, or cloud provider. Any inventory is explicitly declarative, not a live-health or integration claim.

Requirements: Python 3.11+; no third-party packages.

```sh
python -m unittest discover -s tests -v
python -m phicloud.server --port 8769
# In another terminal:
curl http://127.0.0.1:8769/healthz
curl http://127.0.0.1:8769/v1/services
```

The server always binds to `127.0.0.1`; its default public registry has no account, mailbox, remote request or mutating API. The optional R3 profile test endpoint performs fresh localhost-only OAuth introspection and is disabled unless explicitly configured. `/healthz` checks **only the registry process**, not whether any service is online. Service stage values are planning/integration labels, not observations. Do not expose this unauthenticated prototype directly to the internet.

## PhiShield R0: local ANC-linked policy candidate (prototype)

The PhiCloud repository now contains an **in-process, side-effect-free
PhiShield policy consumer** at `phicloud/shield_policy.py`. It validates
ANC's versioned risk advisory alongside independent, request-bound
authority and consent evidence, then returns only `DENY`, `REVIEW`, or
`CANDIDATE`. It never grants execution authority.

The new CI interoperability job fetches ANC at an **exact commit**
and verifies real ANC-generated advisory envelopes against PhiCloud's
independent consumer. The existing registry HTTP server remains
**read-only**, unauthenticated and **does not expose a policy endpoint**.
This is not working PhiID authentication, live PhiShield enforcement,
or a remotely accessible security API.

See [the PhiShield R0 trust boundary](docs/PHISHIELD_ANC_LOCAL_R0.md).
Test locally with `python -m unittest discover -s tests -v`.

## PhiShield R1: authenticated local ANC advisory (prototype)

The opt-in [local authenticated advisory envelope](docs/PHISHIELD_AUTHENTICATED_R1.md)
wraps ANC R1 risk evidence with a standard HMAC-SHA256 message authentication
tag, bounded validity period, request/audience binding and a single-process
nonce replay check. It is verified **before** the existing PhiShield
`DENY` / `REVIEW` / `CANDIDATE` policy consumer.

This is still a local test boundary. No trusted key-management service,
OIDC verifier, remote authentication, durable replay store, live policy API,
or PhiOS execution permission is created. The existing local registry
continues to expose **read-only declarations only**.

`python -m unittest discover -s tests -v` tests it; the existing pinned
ANC cross-repository CI smoke also exercises the authenticated handoff.
